# Perbaikan audit Oktober 2026

Laporan pengerjaan audit UX dan konsistensi data untuk pengalaman calon penghuni. Semua perubahan sudah
diterapkan di repo, diuji, dan diverifikasi di browser terhadap build produksi lokal. **Belum** ada yang
di-commit, di-push, atau diterapkan ke database Supabase cloud; langkahnya ada di bagian 8.

## 2. Cara meninjau

Preview lokal (database Supabase lokal, data contoh terbaru):

```bash
npx supabase start
npx supabase db reset
npm run dev
```

Buka `http://localhost:3010`. Halaman yang paling berguna untuk ditinjau:

- `/` hero dari data asli
- `/cari?area=binus-kemanggisan&urut=termurah` urutan murni + blok promosi
- `/kos/kost-anggrek-cakra` pilih tipe kamar AC (penuh) di Ringkasan
- `/kos/kos-om-deddy` biaya listrik belum diketahui
- `/banding?kos=kost-anggrek-cakra:7828a450-e5ab-4072-a337-c6c7a3bc6407,kos-putri-melati` banding per tipe kamar
- `/cari?area=binus-kemanggisan&harga_min=2000000&harga_max=1500000` rentang harga tidak valid
- `/cara-kami-menilai` rumus, aturan biaya, batas pengukuran, data contoh

Tangkapan layar ada di `docs/tangkapan/audit/`.

## 3. Temuan per prioritas

Status: **Selesai** = diterapkan dan diverifikasi; **Sebagian** = diterapkan dengan batas yang dijelaskan.

### P1 Konsistensi data — Selesai

| Temuan | Akar masalah | Perbaikan |
|---|---|---|
| Hero 8,1 / "Kedap suara" vs listing 6,9 / "Berisik" | `HeroVisual` berisi angka yang diketik tangan | Hero memakai `kos_kartu` listing nyata (`app/(user)/page.tsx`), `hitungBiaya`, `chipKebersihan`, `chipKedap`, `kataSelisihDb` |
| Gypsum di pengukuran, "bata plester" di catatan | `generate.ts` memilih catatan acak | Catatan bersyarat + catatan wajib saat ukur ekstrem (`supabase/seed/generate.ts`) |
| "Mayoritas mahasiswa" vs "karyawan shift" | Sama | Catatan mayoritas mengikuti `kos_aturan.mayoritas_penghuni` |
| Label kebersihan berbeda antar bagian | Kartu pakai ambang sendiri ("Bersih" ≥ 4), detail pakai `lib/skala` | Semua chip dan kata lewat `lib/skala.ts`; kata kedap diseragamkan ("Kedap suara", "Cukup kedap", "Berisik"); ambang dB diselaraskan dengan rubrik kedap |
| Data ukur dan narasi tercampur | — | Bagian ukur diberi tanggal survei, kamar yang diuji (`kos_penilaian.kamar_diukur`), dan batas pengukuran; catatan surveyor diberi keterangan "kesan, bukan hasil ukur" |
| Kontradiksi serupa di data lain | Dicek otomatis | pgTAP memeriksa: "nyaris tidak terdengar" hanya di kedap ≥ 4 bertembok bata/hebel, catatan mayoritas, jam malam, red flag "tidak ada penjaga" vs data penjaga dan fasilitas. Ditemukan dan diperbaiki: Pondok Sakinah (red flag "tidak ada penjaga" tetapi tercatat ada penjaga), red flag "lantai 2" di kos satu lantai, deposit beda aturan antar tipe kamar di kos yang sama, bulan bayar di muka melebihi kontrak minimal |

Kriteria selesai terpenuhi: angka dan label dihitung dari satu sumber (`lib/biaya.ts`, `lib/kamar.ts`,
`lib/skala.ts`, view `kos_skor`/`kos_kartu`), jadi mengubah data listing memperbarui semua tampilan.

### P2 Tipe kamar dan ketersediaan — Selesai

- ID stabil: `tipe_kamar.id` (UUID), dibawa di URL `?kamar=` dan di simpan/banding.
- Status per tipe: `statusKamar()` → Tersedia / Penuh / Belum dikonfirmasi, dengan tanggal konfirmasi.
- Kartu dan pencarian memakai **kamar acuan**: tipe termurah yang masih ada kamar, sehingga harga, nama tipe,
  dan status di kartu selalu milik kamar yang sama.
- Detail: pemilih tipe (radio, bisa panah keyboard) di Ringkasan dan Rincian biaya; sidebar memisahkan
  "Kamar AC: Penuh, 0 dari 6" dari "Seluruh kos: 4 kamar kosong, 2 tipe".
- Tombol kontak: "Chat pemilik" / "Tanya kapan tersedia" / "Tanya ketersediaan", pesan WhatsApp ikut tipe dan status.

### P3 Banding — Selesai

- Format `?kos=slug:kamarId,…` (`lib/kos/kunci-banding.ts`); entri lama `?kos=a,b` dan localStorage lama tetap terbaca.
- Kepala kolom: nama kos, tipe penghuni, pemilih tipe kamar, asal pilihan ("Tipe kamar pilihanmu",
  "Dipilih otomatis: termurah yang masih ada kamar", atau "Tipe kamar di tautan ini sudah tidak ada").
- Baris "Untuk" dan "Pasangan" selalu tampil di mode hanya perbedaan; "campur" tidak dianggap boleh pasangan.
- Ponsel: blok "Ringkas" berdampingan, lalu tabel lengkap dengan header dan kolom label yang menempel.
- Batas tiga kandidat dan tampil/sembunyikan "hal yang sama" dipertahankan.

### P4 Urutan dan promosi — Selesai

- `cari_kos_v3`: Termurah (total ↑, total belum lengkap di bawah), Terdekat (jarak ↑), Skor tertinggi (skor ↓,
  belum dinilai di bawah); seri diputus jarak lalu id. Paling relevan: ada kamar → data segar → paket berbayar →
  skor → jarak, dijelaskan langsung di bawah kontrol urutan.
- `kos_promosi`: maks. 2 spotlight yang lolos filter yang sama, ada kamar, data segar; blok berlabel
  "Promosi berbayar" dengan penjelasan. Label "Mitra" menjadi "Mitra berbayar".
- Jarak: di pencarian kampus/stasiun atau titik peta, kartu menulis jarak garis lurus ke tujuan yang dipilih;
  menit jalan kaki hanya ditampilkan bila patokannya sama.

### P5 Harga, estimasi, uang masuk — Selesai

- `formatRupiahRingkas` tanpa pembulatan (uji properti 500 rb–3 jt).
- `hitungBiaya()` satu-satunya perhitungan total; SQL `total_bulanan` dicek sama di 77 tipe kamar.
- Kolom baru `total_lengkap` dan `total_estimasi`; biaya belum diketahui tidak lolos filter harga dan berada
  paling bawah di Termurah.
- `hitungUangMasuk()`: total bulanan × bulan di muka + deposit + biaya sekali bayar, masing-masing sekali.
  Kontrak minimal ditulis terpisah. Ketentuan pengembalian deposit ditampilkan.

### P6 Validasi filter — Selesai

`bacaRupiah()` menerima "1.500.000", "Rp 1.500.000", "1,5 jt", "850rb"; menolak negatif dan teks. Error muncul
di bawah kolom (`role="alert"`, `aria-invalid`, `aria-describedby`), angka tetap, tombol berubah menjadi
"Perbaiki rentang harga" yang memindahkan fokus ke kolom bermasalah. URL dengan rentang terbalik menampilkan
panel error dengan tombol "Tukar" dan "Ubah di filter". Saran hasil kosong dipertahankan dan diverifikasi
jumlahnya cocok.

### P7 Makna skor — Selesai

Rubrik transparansi baru (SQL `kos_skor` + `lib/scoring.ts`, `KRITERIA_TRANSPARANSI`):

1. Kontrak minimal dan jumlah bulan bayar di muka disebutkan
2. Setiap biaya wajib bulanan punya nominal; listrik berbasis pemakaian punya estimasi
3. Ketentuan deposit dan semua biaya sekali bayar jelas
4. Harga dicek dalam 90 hari (kolom `harga_dikonfirmasi_pada`, distempel otomatis saat harga berubah)

Nilai = rata-rata semua tipe kamar dari 1,25 × cek terpenuhi. Semua skor dihitung ulang otomatis (view).
`/cara-kami-menilai` kini memuat rumus, pembulatan, penanganan data hilang, aturan biaya, batas pengukuran
kebisingan, dan aturan paket berbayar. Rincian skor di detail menampilkan keempat cek untuk kamar terpilih.

### P8 Ringkasan keputusan dan responsivitas — Selesai

- Blok "Ringkasan" di detail: untuk siapa (+ aturan pasangan), tipe kamar, biaya bulanan dan status estimasi,
  uang masuk, ketersediaan tipe, tanggal survei, tiga kelebihan dan tiga kekurangan dari data (`lib/kos/ringkasan.ts`).
- Panel banding memberi ruang di alur halaman dan diletakkan di atas bar kontak dengan safe area; target sentuh
  kecil diperbesar ke 44 × 44 lewat utilitas `sentuh` tanpa mengubah tampilan.
- Diuji di 320, 375, 768, 1280 px, landscape 812 × 375, dan teks 200%: tanpa scroll horizontal halaman.

### P9 Aksesibilitas dan feedback — Selesai

- Fokus kembali ke pemicu setelah dialog, lightbox, dan tur 360° ditutup (`lib/fokus.ts`).
- Lightbox: panah kiri/kanan berfungsi sejak dibuka.
- Tur 360°: petunjuk terlihat, tombol putar dan zoom 44 px, tombol "Coba muat lagi" saat gagal.
- Peta: status "Memuat peta…" dan panel gagal dengan "Coba lagi".
- Pesan simpan: "… tersimpan di perangkat ini"; halaman Disimpan menyebut data tidak dikirim ke server.
- Kontras: status hijau pada kartu tipe kamar terpilih sempat 4,39:1, diperbaiki (latar putih).

### P10 Data demo, SEO, performa, keamanan — Selesai, performa dengan catatan

- **Data demo**: `MODE_DEMO` (`NEXT_PUBLIC_MODE_DEMO`, aktif bila kosong). Banner prototipe, penanda "Data contoh"
  di blok survei, ilustrasi diberi label dan alt "Ilustrasi contoh: …", klaim "Tim kami baru saja datang" dan
  "47 kos disurvei" diganti untuk mode demo, tombol kontak menampilkan pesan tanpa membuka WhatsApp.
- **SEO**: deskripsi meta menyebut total dengan benar (lengkap/estimasi/sementara); JSON-LD di-escape,
  memakai `NEXT_PUBLIC_SITE_URL`, dan tidak diterbitkan untuk data contoh (Product/Offer dan FAQ statistik area).
  Canonical, sitemap, dan robots dicek; kebijakan pengindeksan tidak diubah.
- **Keamanan**: lihat bagian 6.

## 8. Performa

Alat: Lighthouse 12.8.2, profil mobile bawaan (simulasi 4G lambat, CPU 4×), Chrome 150 headless, MacBook
M4 Pro. Server: `next start` lokal dengan database Supabase lokal, data yang sama. Median 3 run per halaman.
Ini **data laboratorium**, bukan data pengguna nyata (belum ada RUM); satu skor tidak berarti semua pengguna
mendapat pengalaman yang sama.

| Halaman | Skor sebelum | Skor sesudah | LCP sebelum | LCP sesudah | CLS | Transfer |
|---|---:|---:|---:|---:|---:|---|
| Beranda `/` | 96 | 95 | 2,84 s | 2,92 s | 0 | 304 → 311 KB |
| Cari `/cari?area=binus-kemanggisan` | 94 | 94 | 3,14 s | 3,14 s | 0 | 321 → 324 KB |

berisi data dan keterangan, ditambah banner prototipe; selisih LCP sekitar 0,1 s pada profil simulasi, masih
dalam rentang variasi antar-run.

## 9. Langkah deploy (dikerjakan pemilik repo)

1. Commit dan push perubahan (lihat daftar file di `git status`).
2. Terapkan migrasi ke Supabase cloud: `npx supabase db push` (dua migrasi baru, hanya menambah; frontend lama tetap jalan).
3. Samakan data contoh cloud tanpa reset: `npx supabase db query --linked -f supabase/sinkron/20261003_data_contoh.sql`.
4. Setelah Vercel selesai build: redeploy bila perlu dan purge Data Cache supaya halaman statis tidak memakai data lama.
5. Setelah frontend baru live, fungsi `cari_kos` lama boleh dihapus lewat migrasi berikutnya.

## 10. Keterbatasan dan yang butuh data nyata

- Semua kos, nomor, surveyor, dan hasil ukur adalah data contoh. Rubrik dan tampilan siap, tetapi klaim
  survei baru sah setelah survei sungguhan; `NEXT_PUBLIC_MODE_DEMO=0` hanya saat itu.
- Metode ukur kebisingan (aplikasi desibel ponsel, satu kamar, satu jam) dijelaskan apa adanya; untuk klaim lebih kuat perlu alat terkalibrasi dan beberapa titik ukur.
- Foto masih ilustrasi; per tipe kamar belum ada foto sendiri.
- Ketersediaan dan harga hanya sesegar konfirmasi pemilik; cache ISR (10 menit beranda, 1 jam detail) masih bisa
  membuat halaman sempat berbeda sampai revalidasi. Webhook revalidasi ada di backlog.
- `klik_wa` dan `kunjungan_kos` belum punya rate limit per IP; perlu di edge (Vercel) atau fungsi server.
- Performa pengguna nyata belum terukur (Plausible/RUM belum aktif).
- Database cloud dan preview Vercel belum diperbarui (menunggu commit dan langkah bagian 9).
